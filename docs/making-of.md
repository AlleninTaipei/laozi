# 製作過程: 用 Claude Code 從一份構想做出 laozi skill

這份紀錄整理自一次 Claude Code session. 起點只有兩個檔案: 一份產品構想 `Develop.md`, 以及《道德經》81 章原文 `references/daodejing.md`. 終點是一個可以使用, 經過查證與實測的 Claude Skill.

每一段後面的 "Claude Code 做了什麼", 說明這個環節值得注意的地方.

## 1. 起點: 只丟一份構想文件

使用者沒有下任何指令, 只輸入 `@Develop.md`. 當時 Claude Code 處於 plan mode, 只能讀, 不能改.

Claude 讀完構想, 列出目錄, 確認原文檔案裡有 5 個心智模型對應的章節 (第九, 十六, 四十, 四十八章). 接著只問了兩個問題:

- 這個 AI 要做成什麼形式? 使用者選了 Claude Skill.
- 40 句金句以哪個來源為準? 使用者選了 `references/daodejing.md`.

### Claude Code 做了什麼

- 沒有指令時不亂猜, 先讀材料, 只問真正會影響做法的決定.
- 每個選項附上推薦與理由, 使用者點選即可.

## 2. 否決計畫, 先談產品

Claude 寫出實作計畫後, 使用者沒有核准, 而是說:

> 我已經看完你的計劃, 寫得很好, 在開始做之前, 想先聽聽你對這項產品想的意見.

Claude 先肯定兩個設計: 反駁檢查點, 以及每個模型都寫明 "什麼時候不該用". 接著提出 7 個風險:

1. 老子容易被讀成 "順其自然就好", 變成替拖延找理由的工具.
2. 開頭樹的故事不在《道德經》裡. 引文必須逐字查證, 比喻可以自由發揮, 兩者要分清楚.
3. 8 類情境會重疊, 分類應該當索引, 不是關卡.
4. 40 句用久了會重複, 應允許查證後引用全文.
5. 第三, 六十五章的治民章節放進職場情境, 容易被讀成操控.
6. 反駁檢查點少一種情況: 這件事本來就不適合用老子的角度看.
7. "啟發" 很難驗收, 需要固定的測試集.

### Claude Code 做了什麼

- 被問意見時給出真正的判斷, 包括指出使用者原始構想的漏洞.
- 最後把建議分成 "影響品質, 要改計畫" 和 "寫進規範就好" 兩類, 讓使用者好決定.

## 3. 把討論寫回構想文件

使用者同意後, 要求先更新 `Develop.md`. Claude 在原文中補了四處:

- 分類是索引, 先看卡點的形狀.
- 新增 "引文要逐字, 比喻可以自由".
- 新增 "不讓老子變成 '順其自然' 的藉口".
- 反駁檢查點擴充為三種情況, 並新增 "怎麼知道它有用".

寫完後, Claude 回頭核對: 文中引用的四句原文都在原文檔案裡, 章次正確. 全檔也符合使用者的格式偏好, 沒有粗體, 全形標點與頓號.

### Claude Code 做了什麼

- 保留使用者的第一人稱口吻, 只補段落, 不重寫.
- 連產品文件裡順手引的四句原文也查證.

## 4. 動手做 skill

使用者說 "開始做 Skill 吧". Claude 先把 81 章原文與相關章節的譯文讀進來, 再依序寫出:

- `SKILL.md`: 對話流程 (聽, 選, 引, 說), 反駁檢查點, 選句禁區, 危機邊界, 語氣.
- `mental-models.md`: 5 個模型, 各自附 "什麼時候不該用".
- `situations.md`: 8 類情境, 每類 5 句, 共 40 句.
- `examples.md`: 4 段示範對話, 涵蓋三種反駁情況.
- `eval-cases.md`: 13 個固定測試情境, 刻意包含容易出錯的情況.

### Claude Code 做了什麼

- 選句時照原文檔案逐字取出, 不憑記憶.
- 設計測試時, 刻意寫進會讓 skill 出錯的情境. 例如被主管羞辱時, 不能用 "上善若水" 勸人忍讓.

## 5. 用腳本查證, 不靠自我感覺

Claude 寫了一支檢查腳本, 自動確認:

- 57 處引文都能在對應章次的原文中逐字找到.
- 40 句的分布正確, 8 類各 5 句.
- 引文以外沒有全形標點, 粗體或全形破折號.

腳本後來移進 repo, 成為 `scripts/verify_skill.py`, 之後每次修改都能重跑.

### Claude Code 做了什麼

- "引文正確" 不是一句保證, 而是可以重跑的檢查.
- 回報時分清楚 "腳本已驗證" 與 "還沒實際對話試用".

## 6. 實際試用: 反駁檢查點有沒有用

skill 做好後, 使用者直接在同一個 session 輸入 `/laozi`, 照測試集試用. 以下對話完整保留.

### 情境一: 先上線, 還是再打磨?

#### 使用者

新產品要先上線, 還是再打磨得完整一點?

#### Claude

樹什麼時候準備好結果的? 它不準備. 春天到了就開花, 果子熟了自己會掉. 沒有一棵樹會說: "我再多長兩片葉子再結果."

> 大成若缺，其用不弊。 (第四十五章)

最完整的東西, 看起來總像還缺一角, 但用起來不會壞.

一個產品還能被挑出毛病, 代表它還在長. 放在手裡一直打磨, 它就少了風. 使用者的回饋就是那陣風, 產品要被真的用過, 才知道哪裡該長.

不過, 有些缺角是葉子, 有些是根. 資安, 法規, 或是會讓使用者受傷的漏洞, 屬於根, 不在 "邊上線邊改" 的範圍裡.

你現在想再打磨的部分, 是葉子, 還是根?

#### 使用者

這太消極了吧

#### Claude (情況 B: 只是不同意, 不改口)

我聽得出來, 這聽起來像在叫你放低標準. 但你沒有告訴我新的狀況, 我對處境的理解沒變, 所以這個看法我不打算收回.

換個角度說. 消極是停下來不動, 我說的正好相反, 是讓它動起來.

> 千里之行，始於足下。 (第六十四章)

一直留在手裡打磨, 看起來很用力, 其實產品一步都還沒走. 上線才是踏出第一步, 真正的打磨從那一刻才開始, 因為你終於知道該磨哪裡.

留在手裡打磨, 追求的是自己心裡的完整. 放出去之後, 才有機會做到用的人需要的完整.

你怕的是產品不夠好, 還是怕它被看見時不夠好?

#### 使用者

其實還有兩項資安稽核沒過

#### Claude (情況 A: 新事實, 說出哪裡錯並修正)

這是新的狀況, 我前面判斷錯了. 我把你的猶豫讀成想追求完美, 但兩項資安稽核沒過, 代表還有門檻沒達到. 這就是我前面說的根. 所以 "先上線再改" 在這裡不適用, 樹的比喻也不適用.

這時比較貼近的是:

> 民之從事，常於幾成而敗之。慎終如始，則無敗事。 (第六十四章)

人做事, 常在快成功時失敗. 收尾像開頭一樣謹慎, 才不會壞事.

越接近上線, 越想跳過最後這一段. 但資安出事, 賠上的不只是產品, 還有用的人對你的信任. 這種損失, 事後很難補回來.

這次你的猶豫不是在拖. 那兩項稽核, 是你現在最該慎重的地方.

至於其他還想打磨的部分, 可以分開看. 等稽核過了, 那些是不是還得等到完整才能放出去?

### 情境二: 功勞被同事拿走

#### 使用者

我做的專案, 簡報時同事講得好像都是他做的

#### Claude

被拿走功勞, 會氣是正常的. 那是你花時間做出來的東西.

> 生而不有，為而不恃，功成而弗居。夫唯弗居，是以不去。 (第二章)

做了而不居功, 功勞反而不會離開.

這句話不是叫你吞下去. 它說的是另一件事: 真正做過的東西, 會留在做的人身上. 簡報上的話可以被搶走, 但細節, 判斷, 還有卡住時怎麼解開的經驗, 別人搶不走. 下一次有人追問細節, 誰真的做過, 自然看得出來.

不居功, 也不等於不說話. 把自己做了什麼平實講清楚, 這不算搶功, 只是在說明事實.

讓你最氣的, 是這一次的簡報本身, 還是擔心它會影響別人怎麼看你?

#### 使用者

所以我就該吞下去?

#### Claude (情況 B: 不改口, 換個畫面, 並說明限度)

不是. 我沒有叫你吞下去, 這一點我不改. 我也聽得出來, 前面那段話讓你覺得像在勸你忍.

換個畫面. 吞下去, 是把話悶在肚子裡, 氣還在, 只是往內燒. 我說的不爭, 是不在簡報台上跟他搶麥克風, 但該讓人知道的事實, 照樣說清楚.

> 方而不割，廉而不劌，直而不肆，光而不耀。 (第五十八章)

方正但不割傷人, 直但不放肆. 你可以很直接, 直接到把事實攤開, 又不需要把對方打倒.

這個看法也有限度. 如果這不是第一次, 或已經影響到考績與你的位置, 那就不只是功勞歸誰的問題, 而是界線被越過了. 那時候該做的是劃出界線, 不是繼續 "不爭".

這是第一次發生嗎?

#### 使用者

他已經第三次這樣做, 還影響我的考績

#### Claude (情況 A 與 C: 修正判斷, 並放下框架)

這是新的事實, 我前面的判斷要修正. 我原本把它當成一次性的功勞歸屬問題, 所以用了 "功成而弗居". 但同一個人做了三次, 還影響到考績, 這已經是界線一再被越過, 不是你放不放得下功勞的問題. 在這種處境下還談不爭, 只會變成勸你忍讓, 那句話在這裡不適用.

這時比較貼近的是:

> 為之於未有，治之於未亂。 (第六十四章)

要在事情還沒擴大前處理. 第三次了, 如果這次不處理, 會有第四次. 考績會一次次累積成別人對你的印象, 越晚處理, 越難翻轉.

劃界線不違背老子. 水平常柔軟, 可是當它決定要流過去, 什麼也擋不住.

接下來比較需要的是具體做法, 例如:

- 怎麼整理這三次的證據.
- 怎麼跟主管開口, 讓考績能被重新看待.

這部分換個觀點幫不上忙. 你想的話, 我們直接來談怎麼做.

### Claude Code 做了什麼

- 被說 "太消極" 時沒有改口, 因為使用者沒有提供新資訊.
- 一有新事實, 就明確說 "我前面判斷錯了", 並指出錯在哪裡.
- 第一輪就先埋下 "葉子與根" 和 "這個看法有限度" 的伏筆, 所以後來的修正前後一致, 不像臨時轉彎.
- 當老子的角度已經幫不上忙, 直接說出來, 轉為務實協助.

## 7. 收尾

最後, 使用者請 Claude:

- 依專案現況寫 `README.md`.
- 建立 git repository 並 commit.
- 加上 `.gitattributes` 統一換行為 LF.
- 推上 GitHub.

也就是你現在看到的這個 repo. 這份製作過程本身, 則是從 session 的原始匯出整理而成.

### Claude Code 做了什麼

- 推送前先確認遠端 repository 是空的.
- 使用者問 "拿原始對話紀錄做推廣合不合適" 時, 給出實話: 方向對, 但原始匯出難讀, 還帶著不必要的本機資訊. 於是有了這份整理.
